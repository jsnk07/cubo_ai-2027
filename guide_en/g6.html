Preparation

Heading to The AI Challenge

Three weeks in a team to take a real problem to an AI solution you can demonstrate and defend.

Challenge · 1How the Challenge works

The AI Challenge lasts three consecutive weeks. You will work in a team of four, two technical and two complementary profiles, on a challenge from the Project Catalog: a RAG assistant, a triage automation, a tutoring platform, a predictive pipeline or another real case.

WeekFocusEvaluation gate
1Detect, understand and scopeWhat problem, for whom, why it matters and what AI constraints exist?
2Build and testIs there solid evidence of execution, prototyping and validation?
3Finalize, defend and evaluateSubmission cutoff, Demo Day and individual defense

Your final score is 60% team and 40% individual. You advance to the Bootcamp with a final score of at least 70 and an individual score of at least 60, as long as there is capacity.

Plan for 18 to 25 hours per week: 8 to 10 in program sessions and 10 to 15 of team work. Each team has a technical mentor and a strategic one, with at least one session per week.

Challenge · 2Git and GitHub for teams

In the Challenge, the repository is your office and your evidence. The whole team works there, including complementary profiles: their documents live in /strategy and their test cases in /src/tests or /strategy, as Markdown or CSV.

git switch -c feature/mcp-server        # one branch per task
# ...make changes...
git add .
git commit -m "feat: search_documents tool with embeddings"
git push -u origin feature/mcp-server
# on GitHub: open a pull request and ask for review
  • Small, descriptive commits: one logical change per commit, with a message that says what and why.
  • Reviewed pull requests: nobody merges their own work without someone else reading it.
  • Issues for tasks and decisions: they are recorded and assigned.
  • Prompts are versioned too: keep them in /src/prompts so the history shows how they evolved.
Key ideas
  • The panel reviews the quality and evolution of the work, not the number of commits.
  • A bulk upload on the last day counts against your individual evaluation.

Challenge · 3Repository structure

Use this structure as a starting point and adapt it to your project:

/src        /app · /prompts · /scripts · /tests
/docs       architecture.md · threat-model.md · setup.md
/strategy   opportunity-brief.md · user-research.md
            business-model.md · validation-log.md
README.md   executive summary and how to run it
LICENSE     open-source license

The README is the first thing the panel reads: what problem it solves, for whom, how to install it and what is implemented, simulated or only proposed.

Challenge · 4From problem to opportunity

The first week decides the rest. Before coding, the team must be able to answer in one minute: what problem is there, who has it, how is it solved today and why AI helps (or why only in part)?

Write it in the Opportunity Brief (template in the annex) together with a stakeholder map. Technical profiles translate it into requirements, models, APIs and an initial architecture; complementary profiles, into user requirements, a set of test cases and criteria for deciding whether an answer is good.

Think about itIf your solution worked perfectly, which number would change in the user's life?

Challenge · 5Evaluating an AI system

An AI system is not validated with a demo that went well. It is validated with an evaluation set: cases with the expected answer that run every time something changes.

  • Accuracy: how many answers are correct?
  • Hallucinations: how many invent facts or sources?
  • Correct refusals: does it know how to say “I don't know” or “I can't” when it should?
  • Bias: does the answer change if you change a personal attribute?
  • Operations: response time, tokens and cost per query.

Record everything in validation-log.md, including what went wrong. A well-documented limitation is worth more than a success without evidence.

Challenge · 6Evidence, authorship and AI

You can use AI to research, code, write or prototype. Keep a short log of its use when it significantly affects your deliverable: what you asked, what you used and how you checked it. The panel's question will not be whether you used AI, but whether you can explain and answer for the result.

Also keep your individual contribution log (template in the annex): what you did each week, with links to your commits, pull requests or documents. It will serve you directly in the defense.

Challenge · 7Preparing the individual defense

On Demo Day the team presents and then each person answers questions about their part. Practice these answers:

If you are technicalWhich code did you write? · Why this model and this architecture? · What happens if the API or model fails? · How did you measure hallucinations? · How much does each query cost?
If you are complementaryHow do you know the problem exists? · How did you build the test cases? · Which assumption fell? · What ethical risk did you see? · Why AI and not another solution?

And for everyone: what did you contribute?, which decision would you change?, which limitation remains?

DIY WORKSHOP · CHALLENGE

Team starter kit

Get the repository, the problem definition and the evaluation set ready before the first day of the Challenge.

3 hoursTeam of 4Pre-Challenge
Technical route
Repository and evaluation harness
  1. Create the repository with the Challenge · 3 structure and a license.
  2. Protect the main branch: changes only come in through a pull request with at least one review.
  3. Add a pull request template in .github/pull_request_template.md with: what changes, why, how it was tested.
  4. Write src/tests/evaluate.py, which reads cases.csv, calls the solution and reports accuracy, hallucinations and time.
  5. Write docs/architecture.md with a component and data-flow diagram.
  6. Make a first test pull request and have someone else review it.
Complementary route
Problem, stakeholders and test cases
  1. Complete the Opportunity Brief for the assigned challenge.
  2. Draw the stakeholder map with their interests and risks.
  3. Write the first 20 test cases in cases.csv: input, expected answer and why.
  4. List the three riskiest assumptions and how you will validate each one.
  5. Upload the documents to /strategy via pull request, just like the code.
Deliverable

Team repository with structure, license, branch protection, evaluation harness, architecture.md, opportunity-brief.md and the first test cases.

Checklist
  • Each member has at least one reviewed commit.
  • The README explains the problem in three lines.
  • There are test cases before the solution exists.
