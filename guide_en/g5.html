F5.1Understanding large language models (LLMs)

An LLM is a neural network trained for a simple task: predicting the next piece of text. The text is split into tokens (word fragments), each token becomes a vector of numbers, and the Transformer architecture uses an attention mechanism to decide which parts of the previous text matter for predicting the next one.

Trained on huge amounts of text and then tuned to follow instructions, that predictor learns to summarize, translate, reason step by step and write code. But it keeps its limits:

  • Context window: it only “sees” a limited number of tokens at a time.
  • Frozen knowledge: it does not know what happened after its training or what is in your documents.
  • Non-deterministic: with a high temperature, the same question can give different answers.
  • Cost per token: every input and output token consumes compute and, in paid services, money.
Key ideas
  • Tokens → vectors → attention → next token.
  • For it to know about your data, you have to give it in the context (RAG) or through tools.
Think about itIf a model has an 8,000-token window and your manual has 300 pages, how would you give it the information it needs?

F5.2RAG systems and agents

RAG (retrieval-augmented generation) answers with your documents in three steps:

  1. Index: split the documents into fragments (chunking) and turn each into an embedding, a vector that represents its meaning. Store them in a vector database.
  2. Retrieve: turn the question into an embedding and find the most similar fragments.
  3. Generate: give the model the question together with those fragments and ask it to answer only from them and cite where each fact came from.

An agent goes one step further: the model decides which tools to use and in what order (search documents, call an API, do a calculation) and repeats until the task is done. More autonomy means more capability and also more risk, which is why agents need clear limits and oversight (F3.3).

Key ideas
  • RAG = index, retrieve, generate with citations.
  • Agent = model that chooses tools in a loop until it finishes.
  • RAG quality depends above all on retrieval.
Think about itIf the RAG answers badly, how do you know whether the fragment search or the answer generation failed?

F5.3Model Context Protocol (MCP) and skills

Every application that connected a model with a tool used to write its own integration. The Model Context Protocol (MCP) is an open standard that solves this: an MCP server exposes tools, resources and prompt templates, and any compatible MCP client can use them without extra code.

  • Tools: functions the model can ask to run, such as search_documents or create_ticket.
  • Resources: data the client can read, such as a file or a record.
  • Prompts: reusable templates the server offers.

The server controls which data is accessed and with what permissions: the model never touches your database directly, it only asks for a defined tool to run. Skills are packages of instructions and resources that teach an assistant to do a specific task consistently.

Key ideas
  • MCP separates the model from the tools with a standard contract.
  • The server defines what can be done and with what permissions.
Think about itWhich tool in your institution would you expose first as an MCP server, and what permissions would you give it?

F5.4Systems thinking and scalability

A prototype that works on your computer is not yet a system. For it to be reliable in production you have to think about its parts and how they fail:

  • Components: interface, orchestration, model, retrieval, tools, storage, logs.
  • Failures: what if the model does not respond, takes too long or returns garbage? Retries, timeouts, fallback answers.
  • Continuous evaluation: a fixed set of questions with known answers that runs every time you change something.
  • Observability: logging inputs, outputs, latency, tokens and errors to understand what happens.
  • Scale: how many users at once, how much latency is acceptable, how much each query costs.
Key ideas
  • Diagram first: components, data flows and failure points.
  • Without a fixed evaluation set you don't know whether a change helped or hurt.
Think about itIf your assistant goes from 10 to 10,000 users a day, which part of the system breaks first?

F5.5Infrastructure, compute economics and sovereign AI

Behind every answer there is hardware: GPUs in a data center or on your computer, electricity and cooling. Choosing where a model runs is a technical, economic and strategic decision.

OptionAdvantagesDisadvantages
A cloud provider's APIMost capable models, no own hardware, pay per useData leaves the institution, variable cost, provider dependence
Open model on own or national serversData control, predictable cost, local capacityInvestment in hardware and staff, models sometimes less capable
Small model on the deviceFull privacy, works offlineLimited capability, depends on the user's device

Sovereign AI is the ability of a country or institution to develop, operate and govern AI systems with infrastructure, data and talent under its control. It does not mean avoiding every external service, but being able to choose and having alternatives.

To compare options, calculate the cost per query: input and output tokens per query × price per token (or the cost of hardware and energy spread across queries).

Key ideas
  • Where the model runs decides cost, privacy and control.
  • Sovereignty is being able to choose, not isolating yourself.
Think about itWhich public services should run on national infrastructure and which could use external services?

What is a token and why does it matter?

A fragment of text the model processes. It determines how much fits in the context window and how much each query costs.

Describe the three steps of a RAG system.

Index the documents in fragments with embeddings, retrieve the fragments most similar to the question and generate the answer with those fragments as context.

What sets an agent apart from a simple chat?

The agent decides which tools to use and in what order, in a loop, until a task is done.

What does an MCP server expose?

Tools, resources and prompts that any compatible MCP client can use.

How do you calculate the cost per query of a cloud model?

Input and output tokens per query multiplied by the price per token of each type.

DIY WORKSHOP · F5

Your first agent with RAG and MCP

Connect a local model to your own documents through an MCP server, measure its quality and calculate what it would cost to run. Produces the F5 deliverable.

4–5 hoursPairs recommendedTechnical: Docker + Ollama + MCP
Technical route
MCP server with semantic search and an agent that uses it
  1. With Ollama running (F1), download an embeddings model and install the libraries: 
    docker exec -it ollama ollama pull nomic-embed-text
pip install "mcp[cli]>=2" numpy requests
  2. Put five to ten short Markdown documents in the docs/ folder (for example, a public service's FAQ).
  3. Write server.py: 
    from pathlib import Path
import numpy as np, requests
from mcp.server.mcpserver import MCPServer

API = "http://localhost:11434/api"
mcp = MCPServer("documents")
docs = {p.name: p.read_text() for p in Path("docs").glob("*.md")}

def embed(texts):
    r = requests.post(f"{API}/embed", json={"model": "nomic-embed-text", "input": texts})
    return np.array(r.json()["embeddings"])

E = embed(list(docs.values()))

@mcp.tool()
def search_documents(question: str, k: int = 3) -> list[dict]:
    """Returns the documents most relevant to the question."""
    q = embed([question])[0]
    s = E @ q / (np.linalg.norm(E, axis=1) * np.linalg.norm(q))
    names = list(docs)
    return [{"source": names[i], "text": docs[names[i]]} for i in s.argsort()[::-1][:k]]

if __name__ == "__main__":
    mcp.run()

    The code uses version 2 of the MCP Python SDK. In version 1 the class was called FastMCP and was imported from mcp.server.fastmcp.

  4. Test it with the MCP Inspector, which runs on Node.js: npx @modelcontextprotocol/inspector python server.py. In the Tools tab, run search_documents with a question.
  5. Write agent.py: it receives a question, calls the tool, builds a prompt with the fragments and asks the model to answer only from them and cite the source. If it can't find the answer, it should say “not in the documents”.
  6. Run 15 test questions (10 answered in the documents and 5 not). Record correct answers, invented answers, tokens (prompt_eval_count, eval_count) and seconds per answer.
  7. Draw the architecture and calculate the cost per query on your machine and with a cloud API's published price.
Complementary route
Agent specification, evaluation and costs
  1. Choose a service that an agent with documents could handle, for example guidance on a procedure.
  2. Write the specification: users, questions it must resolve, source documents, MCP tools it would need and actions it cannot take without human approval.
  3. Build the evaluation set: 20 questions with their correct answer and source, including 5 the agent must refuse to answer.
  4. Test it with an AI assistant to which you attach the documents, and score each answer: correct with citation, correct without citation, invented or appropriate refusal.
  5. Build the cost sheet: queries per month, tokens per query and published price of two options (cloud API and open model on own server). Add a sovereignty and risk column.
